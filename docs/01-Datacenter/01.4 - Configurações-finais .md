## Configurações realizadas

### Instalação do Incus

O incus não estava disponível para instalação através dos repositórios oficiais do Rocky Linux, para realizar a instalação dele, se fez necessário habilitar o repositório CRB e adicionar e habilitar os pacotes do Incus hospedados no COPR. Somente então pude realizar a instalação. 

### Criação da Bridge 

O incus permite que através dele, seja criada uma interface bridge que será gerenciada por ele próprio, o que trás algumas facilidades, como dhcp e regras de firewall gerenciadas por ele, entre outras coisas, porem, eu optei por criar uma interface bridge manualmente e apontar o incus a ela. 

Escolhi dessa forma para aprender a fundo o funcionamento de uma bridge. Além disso, dessa forma o controle da bridge e do firewall ficam exclusivamente sobre minha responsabilidade, o Incus não tem controle nenhum sobre ambos, o que me da margem para ter um controle maior sobre o que esta sendo feito no sistema.

Defini o nome da Bridge como br-samba e ipv4 como 10.0.0.1/24, sendo assim a faixa dela ficou 10.10.10.0/24, dei esse nome pois pretendo vincular a ela um container contendo o samba 4. Inicialmente criei somente uma bridge, mas futuramente pretendo criar uma bridge para cada container, gerando assim um isolamento de rede, em que cada container pertence a uma rede diferente. 

### Criação do storage 

Utilizando o volume logico que dediquei ao incus, o montei em uma pasta no /srv e dei o nome da pasta de incus, entao criei uma pool  tambem chamada incus apontando para a pasta. Ela sera utilizada para hospedar os containers e seus arquivos.

### Configuração do User Namespaces

Eu criei um sub ID e GID para o root nos containers que vou criar do incus, a ideia e que o root e demais usuários da SO do container não tenham o mesmo ID e GID do Data Center, dessa forma se ele sofrer uma invasão, o invasor não poderia usar o root ou qualquer outro usuário do container para sair do container ou ter qualquer privilegio sobre o Data Center.

Para isso, adicionei a linha de configuração root:1000000:1048576 nos arquivos /etc/subuid e /etc/subgid, o que essa linha faz e basicamente definir uma faixa de ID e GID que o container pode usar para criar seus usuarios, mesmo que eu crie como root, ela se aplica ao root e demais usuários criados no container, dessa forma, contanto que meu container não seja um container privilegiado, o root ou qualquer outro usuário do container não tem qualquer ação no Data Center, dentro do container o root e ID e GID 0, mas fora dele, no Data Center, o ID desse mesmo root seria um numero da faixa que defini. 

Quando eu for configurar o profile do container, irei utilizar uma configuração chamada security.idmap.isolated, o que faz com que o incus crie um isolamento do ID e GID dos próprios containers, ou seja, cada container terá um ID e GID diferente para o root e demais usuários criados, assim nenhum usuário de nenhum container consegue influenciar o outro. Ele faz isso, separando uma faixa dentro da faixa que eu estabeleci nos arquivos /etc/subuid e /etc/subgid, ele separa 65.536 UIDs e GIDs para cada container, obviamente e preciso configurar nos arquivos uma faixa grande que tenha o suficiente para gerar essa separação. Dessa forma, a segurança aumenta ainda mais. 

### Criação do Primeiro Profile 

O incus me permite configurar um perfil de configuração, ao vincular esse perfil a um container, o container passara a utilizar as configurações que foram definidas no perfil. Inicialmente criei apenas um profile que será dedicado ao uso do container que ira hospedar o samba 4, por isso dei o nome do profile de samba-server.  

No perfil, defini as seguintes configurações:

- Inicio automático do container após boot do servidor
- Limite de 1 núcleo na CPU
- Limite de 1GiB de memoria 
- Limite de 200 processos ativos
- Isolamento de ID e GID nos containers
- Tipo de rede usada será Bridge
- A bridge usada sera a br-samba
- A placa de rede virtual sera uma NIC
- O espaço de disco dedicado será usado no /
- A pool usada será a Incus
- O tipo do armazenamento e disk

### Criação do Primeiro Container

Optei por utilizar containers de sistema na minha infraestrutura e escolhi o Debian trixie como SO do meu primeiro container, seguindo meu planejamento de infraestrutura o primeiro container foi chamado de terra. Vinculei o profile samba-server que criei a ele, então ele ira utilizar as configurações definidas no profile.

Ao iniciar o container o incus cria a placa de rede virtual, porem como não estou usando uma bridge gerenciada pelo próprio Incus, a placa de rede virtual que ele criou não pegou IP de forma automática com DHCP, sendo assim tive que inserir nela um ip de forma manual. Respeitando a faixa da bridge que criei, escolhi o IP 10.10.10.2/24. Então, defini a rota do ip do container na faixa da bridge br-samba do data center, com o gateway sendo o ip da bridge.

### Configuração do Wireguard

Como pretendo acessar o container diretamente sem precisar primeiro realizar login no Data Center, vou configurar posteriormente nele um ssh que so pode ser acessado pela interface do Wireguard. Ja me adiantando, adicionei a faixa de rede da bridge br-samba no arquivo wg0.conf do wireguard, junto do ip do Data Center, dessa forma, ao estar conectado no wireguard, poderei acessar o container via ssh diretamente.

### Configuracao do Firewall

Além das regras de firewall que já existiam, criei novas regras para permitir que o container possa acessar a internet. Inicialmente ele ira precisar desse acesso na rede para que eu possa realizar a atualização da SO e instalar o Samba 4.

Optei por dividir as regras do firewall em arquivos diferentes, ao inves de deixar todas em um único arquivo, como estava antes todas concentradas no arquivo firewall.nft, agora criei o arquivo filter.nft onde vão ficar as tables de filtragem e também criei o arquivo nat.nft onde vão ficar as tables de nat, dessa forma fica mais organizado e mais fácil de configurar. 

As novas regras da tabela filter são:

Input:
- Permite a conexão ssh no container terra, através da interface do Wireguard
- Permite o trafego de rede vindo da interface bridge br-samba

Forward:
- Permite o encaminhando de rede vindo da bridge br-samba para a interface de rede do Data Center ens18.
- Permite o encaminhando de rede vindo da interface do wireguard para a interface bridge br-samba\
- Habilitação de conexões já estabelecidas e relacionadas.

As regras da tabela nat são: 

- Encaminha o tráfego da rede br-samba para fora pela interface de rede do Data Center ens18, sem precisar informar um endereço IP fixo.

### Configuração do Kernel 

Tive que alterar uma configuração do Kernel para que o Data Center pudesse fazer o forward através do IPV4. Mesmo permitindo no Firewall, sem essa configuração do kernel o forward não iria funcionar. 

Realizei essa configuração, criando um arquivo chamado 01-rede.conf na pasta /etc/sysctl.d. Dentro dele, escrevi a regra net.ipv4.ip_forward = 1, que habilita o servidor para funcionar como um roteador e passar pacotes de uma interface de rede para outra. Então executei o comando `sysctl --system` para o kernel recarregar as configurações e aplicar minha regra. 

Daria para alterar também via comando, mas dessa forma a regra só seria valida enquanto o servidor esta ligado, depois de reiniciar o kernel recarrega as configurações e a regra que criei seria desfeita. Fazendo dessa forma, como o arquivo, o sysctl por padrão vai ler os arquivos .conf dessa pasta sempre que o servidor for reiniciado, e vai inserir a regra que criei no kernel.
