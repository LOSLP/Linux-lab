# Configurações de Segurança 

## Objetivo

Realizar as configurações inicias de segurança do sistema. 

## Configurações realizadas

### Criação de Grupo

Realizei a criação do grupo "ssh-users" e atribuí o usuário voyager a ele. O grupo será utilizado na configuração do SSH.

### Arquitetura do SSH  

#### Configuração do SSH

A aplicação OpenSSH foi instalada durante a instalação do servidor. Realizei algumas alterações nas configurações do SSH para reduzir o risco de invasões no sistema.

Por padrão, na imagem escolhida para esse servidor, existe uma lógica de include no arquivo de configuração do SSH, o sshd_config. Essa lógica faz com que o SSHD leia primeiro o conteúdo do diretório sshd_config.d, localizado em /etc/ssh.

Dentro dele existia um arquivo padrão que incluía apenas uma única regra, permitir o login do usuário root via SSH.

Optei por manter essa lógica padrão de configuração do SSH por considerar mais fácil administrar suas configurações. Para isso, alterei o nome desse arquivo para "01-ssh.conf" e modifiquei suas configurações.

Dentro do arquivo coloquei as seguintes regras:

- Bloqueio do login do root via SSH no servidor, habilitando somente o login do usuário voyager.
- Bloqueio de autenticação por senha, sendo possível realizar login somente via chave SSH.
- Habilitação do login via chave SSH no servidor.
- Definição do login via SSH apenas para membros do grupo "ssh-users".
- Definição do número máximo de tentativas de login via SSH como 3.
- Definição da porta do SSH como 22.
- Bloqueio de tunelamento SSH.
- Bloqueio do encaminhamento X11 via SSH.

#### Configuração da Chave de Acesso

Realizei a criação de uma chave de autenticação SSH do tipo Ed25519 utilizando a ferramenta PuTTY Key Generator. Armazenei a chave privada em um local seguro na minha estação de trabalho e armazenei a chave pública dentro do servidor.

O armazenamento da chave foi feito da seguinte forma: realizei a criação de um diretório chamado Authorized_Keys, localizado dentro de /etc/ssh.

Esse diretório tem como objetivo armazenar todas as chaves públicas dos usuários que terão acesso ao servidor. Dentro do diretório haverá um arquivo com o nome de cada usuário e, dentro de cada arquivo, será armazenada a chave individual do respectivo usuário.

A segurança dessa lógica foi feita da seguinte forma: a pasta Authorized_Keys foi configurada como propriedade do usuário root e do grupo root. As permissões da pasta foram definidas como 755.

Os arquivos dentro dela, identificados com o nome dos usuários, possuem como proprietário o usuário root, enquanto o grupo proprietário corresponde ao grupo principal de cada usuário. A permissão desses arquivos foi definida como 640.

Essa lógica foi pensada dessa forma para que os usuários não possam alterar ou apagar suas próprias chaves de login e também para facilitar a auditoria do servidor, uma vez que todas as chaves de acesso ficam concentradas na mesma pasta sob controle exclusivo do root.

Para que o ssh utilize esta pasta, no arquivo de configuração do ssh o sshd_config, existe uma linha de configuração onde e indicado o local onde ele procura as keys publicas, por padrao fica apontado para a home do usuario em ~/.ssh/authorized_keys, entao eu apenas alterei a linha mudando o apontamento para a pasta /etc/authorized_keys.

No meu nível de conhecimento atual, essa foi a melhor solução de segurança que pude desenvolver para a restrição das chaves SSH.

Pensei em fazer dessa forma porque, embora os usuários tenham acesso a essa pasta como leitores e possam visualizar os arquivos permitidos para eles, não são capazes de alterar a pasta nem os arquivos.

Cada usuário pode visualizar sua própria chave, mas não consegue visualizar as chaves dos demais usuários.

Sendo assim, caso o usuário voyager seja comprometido de alguma forma, o invasor poderia acessar a pasta e identificar a existência dos demais usuários, porém não teria qualquer capacidade de modificação dentro dela, sendo possível visualizar apenas a chave pública do usuário voyager e não as chaves dos demais usuários.

### Configuração do PAM

Com o objetivo de aumentar ainda mais as barreiras contra invasões, utilizando o conhecimento que adquiri durante os estudos sobre PAM, criei uma regra para impedir que o usuário voyager utilize o comando `su` para se tornar root.

Se por algum motivo o usuário voyager fosse comprometido, o invasor não poderia utilizá-lo para realizar elevação de privilégios para root através do comando `su`.

Para implementar essa regra, acrescentei uma linha de configuração no arquivo utilizado pelo PAM para controlar o comportamento do comando `su`.

A lógica é bem simples: se o usuário que está executando o comando `su` for o voyager e o usuário de destino for o root, o acesso será bloqueado.

### Configuração do WireGuard 

Realizei a instalação do WireGuard no servidor com o objetivo de que futuramente o acesso ao servidor seja realizado apenas por equipamentos conectados à VPN.

Para a configuração dele, realizei a criação de uma pasta em /etc chamada wireguard. Dentro dela criei duas pastas, uma chamada private_keys e outra chamada public_keys. Dentro delas realizei a criação das chaves tanto do servidor quanto do cliente, no caso minha estação de trabalho Windows, que irá se conectar ao servidor, e as armazenei em arquivos.

Tanto a pasta wireguard quanto as pastas private_keys e public_keys, assim como os arquivos dentro delas, estão sob propriedade do usuário root e do grupo root. A permissão de todas as pastas foi definida como 700 e a dos arquivos como 600.

Também realizei a criação de um arquivo chamado wg0.conf dentro da pasta wireguard. Dentro dele inseri as configurações de interface e cliente que o WireGuard deverá utilizar, sendo elas a PrivateKey, a faixa de IP e a porta de conexão do servidor, além da PublicKey e do AllowedIPs do cliente.

Após o processo de configuração, utilizando o comando `wg-quick up wg0`, o WireGuard aplica as configurações e realiza todo o processo de criação da interface de rede no servidor.

### Configuração do Nftables

Por padrão, o Rocky Linux veio com o Firewalld, porém eu optei por desabilitá-lo e utilizar o Nftables puro na configuração de firewall do meu servidor. Fiz isso porque quero aprender a configurar diretamente as regras de firewall, sem nenhum facilitador.

Tenho ciência de que o Firewalld ajuda bastante em tarefas cotidianas, como bloquear ou permitir portas, entre outras configurações, mas ainda assim prefiro configurar tudo manualmente para criar uma base sólida sobre como o Nftables funciona de fato.

Futuramente, quando já tiver um conhecimento maior, pretendo também aprender Firewalld e irei utilizá-lo nessas mesmas tarefas cotidianas. A diferença é que, como estudei Nftables diretamente, saberei exatamente o que ele está fazendo por baixo dos panos.

Meu objetivo não é apenas decorar comandos, mas entender o que estou fazendo. Hoje vejo o Firewalld como uma barreira no caminho para atingir esse objetivo. Se eu iniciar o aprendizado por ele, acredito que terei dificuldades mais à frente para entender o Nftables. Fazendo o caminho inverso, acredito que não terei grandes dificuldades para aprender o Firewalld posteriormente.

Para a configuração do Nftables, assim como no SSHD, ele vem com um include em seu arquivo de configuração principal, o nftables.conf. Esse include apontava para outro arquivo com configurações padrão do Nftables, todas comentadas.

Para preservar essa estrutura original, criei um novo arquivo na mesma pasta onde se encontrava o arquivo de apontamento original, com o nome firewall.nft, e nele inseri as configurações do servidor, então alterei o apontamento para ele no arquivo nftables.conf.

Dentro do arquivo coloquei as seguintes regras:

- Remoção de todas as regras Nftables já existentes.
- Bloqueio de tudo o que não atende às regras definidas.
- Habilitação da interface de loopback.
- Habilitação de conexão SSH de entrada na porta 22, vinda do IP 10.0.0.2 através da interface wg0.
- Habilitação de conexão UDP de entrada na porta 51820.
- Habilitação de conexões já estabelecidas e relacionadas.
  
As configurações que criei são bem simples, mas acredito que são suficientes neste momento para proteger o que existe hoje no servidor.

Pretendo evoluí-las conforme meu conhecimento aumenta e conforme vou inserindo novos recursos no servidor.
