# Configurações de Segurança 

## Objetivo

Realizar as configurações inicias de segurança do sistema. 

## Configurações realizadas

### Criação de Grupo

Realizei a criação do grupo "ssh-users" e atribuí o usuário voyager a ele. O grupo será utilizado na configuração do SSH.

### Arquitetura do SSH  

#### Configuração do SSH

A aplicação OpenSSH foi instalada durante a instalação do servidor. Realizei algumas alterações nas configurações do SSH para reduzir o risco de invasões no sistema.

Por padrão, na imagem escolhida para esse servidor, existe uma lógica de include no arquivo de configuração do SSH, o sshd_config. Essa lógica faz com que o SSHD leia primeiro o conteúdo do diretório sshd_config.d, localizado em /etc/ssh.

Dentro dele existia um arquivo padrão que incluía apenas uma única regra, permitir o login do usuário root via SSH.

Optei por manter essa lógica padrão de configuração do SSH por considerar mais fácil administrar suas configurações. Para isso, alterei o nome desse arquivo para "01-ssh.conf" e modifiquei suas configurações.

Dentro do arquivo coloquei as seguintes regras:

- Bloqueio do login do root via SSH no servidor, habilitando somente o login do usuário voyager.
- Bloqueio de autenticação por senha, sendo possível realizar login somente via chave SSH.
- Habilitação do login via chave SSH no servidor.
- Definição do login via SSH apenas para membros do grupo "ssh-users".
- Definição do número máximo de tentativas de login via SSH como 3.
- Definição da porta do SSH como 22.
- Bloqueio de tunelamento SSH.
- Bloqueio do encaminhamento X11 via SSH.

#### Configuração da Chave de Acesso

Realizei a criação de uma chave de autenticação SSH do tipo Ed25519 utilizando a ferramenta PuTTY Key Generator. Armazenei a chave privada em um local seguro na minha estação de trabalho e armazenei a chave pública dentro do servidor.

O armazenamento da chave foi feito da seguinte forma: realizei a criação de um diretório chamado Authorized_Keys, localizado dentro de /etc/ssh.

Esse diretório tem como objetivo armazenar todas as chaves públicas e privadas dos usuários que irão utilizar o servidor. Dentro do diretório haverá um arquivo com o nome de cada usuário e, dentro de cada arquivo, será armazenada a chave individual do respectivo usuário.

A segurança dessa lógica foi feita da seguinte forma: a pasta Authorized_Keys foi configurada como propriedade do usuário root e do grupo root. As permissões da pasta foram definidas como 755.

Os arquivos dentro dela, identificados com o nome dos usuários, possuem como proprietário o usuário root, enquanto o grupo proprietário corresponde ao grupo principal de cada usuário. A permissão desses arquivos foi definida como 640.

Essa lógica foi pensada dessa forma para que os usuários não possam alterar ou apagar suas próprias chaves de login e também para facilitar a auditoria do servidor, uma vez que todas as chaves de acesso ficam concentradas na mesma pasta sob controle exclusivo do root.

Essa pasta hospeda tanto chaves públicas quanto privadas porque, mesmo que o servidor principal "sol" só possa ser acessado através do usuário voyager, os demais servidores que ele irá hospedar só poderão ser acessados através do servidor sol.

Dessa forma, essa pasta irá armazenar as chaves privadas utilizadas para acessar os demais servidores. Nesses servidores haverá a mesma estrutura de diretórios, porém contendo apenas as respectivas chaves públicas.

No meu nível de conhecimento atual, essa foi a melhor solução de segurança que pude desenvolver para a restrição das chaves SSH.

Pensei em fazer dessa forma porque, embora os usuários tenham acesso a essa pasta como leitores e possam visualizar os arquivos permitidos para eles, não são capazes de alterar a pasta nem os arquivos.

Cada usuário pode visualizar sua própria chave, mas não consegue visualizar as chaves dos demais usuários.

Sendo assim, caso o usuário voyager seja comprometido de alguma forma, o invasor poderia acessar a pasta e identificar a existência dos demais usuários, porém não teria qualquer capacidade de modificação dentro dela, sendo possível visualizar apenas a chave pública do usuário voyager e não as chaves dos demais usuários.

### Configuração do PAM

Com o objetivo de aumentar ainda mais as barreiras contra invasões, utilizando o conhecimento que adquiri durante os estudos sobre PAM, criei uma regra para impedir que o usuário voyager utilize o comando `su` para se tornar root.

Se por algum motivo o usuário voyager fosse comprometido, o invasor não poderia utilizá-lo para realizar elevação de privilégios para root através do comando `su`.

Para implementar essa regra, acrescentei uma linha de configuração no arquivo utilizado pelo PAM para controlar o comportamento do comando `su`.

A lógica é bem simples: se o usuário que está executando o comando `su` for o voyager e o usuário de destino for o root, o acesso será bloqueado.
